# 缓存模式热点查询对照压测（2026-08-23）

## 实验目的

在同一个 Release 二进制、同一台 Linux 服务器、同一文档、4 Worker、4 I/O EventLoop、相同 wrk 负载下，对比缓存模式的端到端表现：

```text
none      : 不使用缓存，直接本地倒排索引检索
l1        : Worker-local L1 LRU（128 条，10 秒 TTL）
l1-redis  : Worker-local L1 + Redis L2（60 秒 TTL）
```

命令：

```bash
bash scripts/run_cache_benchmark.sh
```

脚本固定使用 `wrk -t4 -c256 -d30s --latency` 请求 `GET /search?q=epoll`，并在每个模式下启动、监控、结束自己的测试服务。每个模式运行 3 次。

## wrk 结果

| 模式 | QPS 三次结果 | QPS 均值 | P99 三次结果 | P99 均值 |
|---|---:|---:|---:|---:|
| `none` | 372,011 / 375,676 / 378,567 | 375,418 | 0.97 / 0.91 / 0.93 ms | 0.94 ms |
| `l1` | 320,029 / 281,286 / 287,505 | 296,273 | 1.24 / 1.29 / 1.34 ms | 1.29 ms |
| `l1-redis` | 279,335 / 291,298 / 279,257 | 283,297 | 1.32 / 1.32 / 1.33 ms | 1.32 ms |

相对 `none`：

- `l1` 平均 QPS 下降约 21%，P99 上升约 38%；
- `l1-redis` 平均 QPS 下降约 25%，P99 上升约 41%。

三轮区间没有重叠：`none` 最低 QPS 372,011，`l1` 最高仅 320,029，因此当前热点工作负载下“不保留缓存优化”的结论稳定。

## pidstat 观察

| 模式 | 平均 %usr | 平均 %system | 平均总 %CPU | RSS 区间 |
|---|---:|---:|---:|---:|
| `none` | 322-334 | 288-292 | 611-626 | 3,944-3,980 KB |
| `l1` | 155-175 | 282-296 | 437-470 | 3,936-3,980 KB |
| `l1-redis` | 158-170 | 285-291 | 443-461 | 3,940-4,008 KB |

`%CPU` 可超过 100%，因为进程内有多个线程；本机有 80 个逻辑 CPU，不能把约 6 个核的使用误称为整机 CPU 饱和。

缓存确实减少了用户态检索/排序/JSON 计算（`%usr` 明显下降），但 `%system` 在三组中几乎持平。端到端 QPS 和 P99 反而变差，说明当前瓶颈并不只是可被缓存跳过的检索计算；socket 收发、epoll、线程调度和缓存热路径的 map/list/锁/字符串操作已占据重要成本。仅凭这些数据不能精确定位到某个系统调用，需要进一步 profiling 才能下更细的结论。

RSS 只有几十 KB 波动，未见缓存对象无限增长或磁盘 I/O。

## Redis 命令观察

首轮 `l1-redis` 的 Redis `INFO commandstats` 增量约为 16 次 GET、1 次 SET。脚本在该模式启动前删除了 `epoll` 的 L2 key，故第一个回源结果写入一次 Redis；L1 的 10 秒 TTL 在 30 秒压力期间使每个 Worker 周期性再次访问 L2。

这说明热点稳态绝大多数请求由 Worker-local L1 吸收，Redis 不会被每次请求访问。因此 `l1-redis` 的退化不能简单归因于 Redis 网络；`l1` 自身已经比 `none` 慢，是当前小型内存倒排索引与高系统态发送成本下缓存不划算的主要证据。

## 工程结论

1. 保留 `none/l1/l1-redis` 模式和两级缓存实现，作为可验证的工程能力与反例；
2. 默认压测结论不是“Redis 缓存优化成功”，而是“先量化再取舍”：当前热点轻查询应选择 `none`；
3. Redis L2 的合理价值要在跨服务实例、Worker 冷启动、远程/昂贵下游（MySQL、RAG、向量检索）以及更大候选集下单独验证；
4. 下一次实验先增加多实例 Redis 共享验证和可控的较重语料，再决定是否为生产默认开启 L2；
5. 若要定位当前 `none` 的上限，应继续做 I/O/Worker 数控制变量实验或在可用权限下进行采样 profiling，而不是盲目叠加缓存。

## 面试表达

“我没有把 Redis 写成简历里的无条件优化。为避免历史数字不可比，我在同一 Release 二进制中加了 `none/l1/l1-redis` 开关，以 4 Worker、4 I/O、256 并发连接各跑 3 次热点压测。无缓存平均约 37.5 万 QPS、P99 0.94 ms；Worker-local L1 约 29.6 万 QPS、P99 1.29 ms；L1+Redis 约 28.3 万 QPS、P99 1.32 ms。缓存降低了用户态计算，但系统态 CPU 几乎不变，且 L1 稳态已吸收绝大多数请求，所以当前小型内存倒排索引下缓存开销超过收益。我保留了可切换实现，并把 Redis 定位为跨实例或昂贵下游的 L2，而不是伪造的单机性能卖点。”
