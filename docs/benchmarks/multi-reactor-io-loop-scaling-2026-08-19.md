# 多 Reactor I/O Loop 扩展压测（2026-08-19）

## 目的

验证主从多 Reactor 是否能缓解单个 EventLoop 负责所有 clientfd 收发与 Worker 结果回传时的排队压力。此前单 Reactor 在高连接数下，单 I/O EventLoop 接近一个 CPU 核，而两个 Worker 尚未饱和。

## 固定条件

| 项目 | 值 |
| --- | --- |
| 构建 | Linux `build-ralease`，`Release` |
| 请求 | `GET /search?q=epoll` |
| 客户端 | `wrk -t4 -c256 -d30s --latency` |
| Worker 数 | 2 |
| 文档目录 | `data/docs` |
| 变量 | `io_loop_count = 1 / 2 / 4` |

每次运行均单独启动服务并在结束后停止，避免不同配置共用进程。

## 结果

| 子 I/O Loop | QPS | 平均时延 | P99 | 吞吐量 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 134,040.38 | 1.91 ms | 2.36 ms | 57.14 MB/s |
| 2 | 224,357.32 | 1.13 ms | 1.59 ms | 95.64 MB/s |
| 4 | 267,406.88 | 0.95 ms | 1.30 ms | 113.99 MB/s |
| 4（复测） | 263,709.76 | 0.96 ms | 1.28 ms | 112.42 MB/s |

`I/O=4` 两次 QPS 差约 1.4%，说明在当前共享机器环境下结果具有基本重复性。

## 线程级 CPU（第一轮）

`pidstat -t -p <pid> 1 31` 的平均值：

| 配置 | Acceptor | 子 I/O Loop | Worker | 总 CPU |
| --- | ---: | --- | --- | ---: |
| I/O=1 | 约 0% | 96.19% | 59.00%、58.58% | 213.87% |
| I/O=2 | 约 0% | 95.90%、95.74% | 74.26%、74.19% | 340.26% |
| I/O=4 | 约 0% | 71.06%、70.39%、70.58%、70.23% | 95.71%、95.77% | 474.00% |

解释：

- Acceptor 只执行 `accept + round-robin`，Keep-Alive 压测期间几乎没有新连接，因此接近空闲；
- I/O=1 时唯一子 Loop 已接近一个核，连接读写和 eventfd 回传存在单核排队；
- I/O=2 后两个子 Loop 都接近满载，吞吐显著上升；
- I/O=4 后 I/O 工作分散到四个线程，但两个 Worker 都接近满载，检索计算与共享任务队列成为下一阶段更值得验证的限制点。

## 内存与磁盘 I/O

最佳配置 I/O=4 的 `pidstat -r -d -t`：

| 指标 | 值 |
| --- | ---: |
| VSZ | 317,972 KB |
| RSS | 3,924 KB |
| %MEM | 0.01% |
| `kB_rd/s` / `kB_wr/s` | 0 / 0 |

搜索索引在启动时构建并常驻内存；压测期间无磁盘读写，说明请求热路径不受文件 I/O 限制。线程增加会扩大虚拟地址空间和栈预留，但当前实际 RSS 仍很低。

## 结论

在 `c256 + Worker=2` 的高并发短检索负载下，多 Reactor 有明确收益：

- I/O=2 相比 I/O=1：QPS `+67.4%`，P99 `-32.6%`；
- I/O=4 相比 I/O=1：QPS `+99.5%`，P99 `-44.9%`；
- I/O=4 相比 I/O=2：仍有约 `+19.2%` QPS，但收益递减；
- 当前瓶颈已从单 I/O Loop 转移到两个 Worker 接近满载，不能继续只增加 I/O Loop。

下一步应固定 `I/O=4`，重新扫描 `Worker=1/2/4`，比较 QPS、P99、线程 CPU、RSS；如果 Worker=4 无收益或退化，需要分析共享 WorkerPool 队列、eventfd 回传与调度成本，而不是盲目扩容。

## 面试表达

“我先用 `wrk + pidstat -t` 证明单 I/O EventLoop 在 c256 下接近单核；随后把连接按 round-robin 分给 2/4 个子 Reactor。在 Worker=2、同一请求与连接数下，QPS 从 13.4 万提升到 26.7 万，P99 从 2.36ms 降到 1.30ms。线程监控显示 4 个 I/O Loop 已不再满核，而两个 Worker 接近满核，因此我据此把下一步优化目标转向 WorkerPool，而不是继续无依据地增加 Reactor 数。”
