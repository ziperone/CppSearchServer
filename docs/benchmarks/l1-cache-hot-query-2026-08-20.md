# L1 LRU 热点查询压测（2026-08-20）

## 目的

验证线程安全 L1 LRU 缓存接入 `/search` 后，是否能降低热点查询的 Worker 计算成本并提升服务吞吐。

## 固定条件

| 项目 | 值 |
| --- | --- |
| 构建 | Linux `build-ralease`，`Release` |
| 服务 | I/O Loop=4，Worker=4 |
| 请求 | `GET /search?q=epoll` |
| 预热 | 压测前用一次 curl 写入 L1 |
| 客户端 | `wrk -t4 -c256 -d30s --latency` |

## 热点 L1 结果

| 次数 | QPS | 平均时延 | P99 | 总 CPU |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 281,140.78 | 0.89 ms | 1.30 ms | 504.45% |
| 2 | 302,309.75 | 0.83 ms | 1.29 ms | 未采样 |

## 与未接 L1 的历史同条件基线比较

此前相同 `I/O=4 + Worker=4 + c256 + epoll` 负载下，未接 L1 的两次结果为：

| 次数 | QPS | 平均时延 | P99 |
| ---: | ---: | ---: | ---: |
| 1 | 361,966.06 | 0.69 ms | 0.97 ms |
| 2 | 379,215.76 | 0.66 ms | 0.98 ms |

虽然跨轮测试会受到共享环境波动影响，但 L1 热点结果两次均显著低于未接缓存基线，且线程 CPU 与实现路径给出了明确解释。

## 线程级解释

热点 L1 第一次测试：

- 4 个 I/O Loop 各约 81%-82%，低于未缓存时约 93%；
- 4 个 Worker 各约 44%，低于未缓存时约 76%；
- Worker CPU 降低证明分词、检索、排序和 JSON 构造确实被缓存跳过；
- 总 QPS 却下降，说明新的共享开销抵消并超过了被跳过的本地检索成本。

当前实现的每个 L1 hit 都要：

```text
竞争一个全局 mutex
    -> unordered_map 查找
    -> 检查 TTL
    -> list::splice 更新精确 LRU 顺序（写操作）
    -> 拷贝 JSON 字符串
```

该操作发生在 4 个 Worker 并发处理的每一次请求中。对于当前极短的内存索引检索，这个共享精确 LRU 的成本高于检索本身。

## 结论与取舍

1. 缓存命中率高不等于吞吐更高；必须对命中路径本身压测；
2. Redis 是网络服务，单机热点微基准下通常比本地 L1 更慢，不能作为解决该锁竞争的理由；
3. Redis 的合理价值在于多个无状态服务实例共享昂贵结果、保护 MySQL/远程检索等下游，而非替代廉价本地计算；
4. 若要优化 L1，应先基于真实混合查询和热点分布选择策略：
   - 每 Worker 本地缓存：消除跨 Worker mutex，但热点结果会重复保存；
   - 分片 LRU：改善多 key 分布下的锁竞争，但单一超热点 key 仍会落在同一分片；
   - 读多写少的近似 LRU：hit 不每次移动 list，允许 shared/read path 并发；
   - 对廉价查询关闭缓存，或只缓存超过阈值的昂贵查询。

当前先保留 L1 的功能与统计作为可选策略，但不把它宣传为当前小索引热点负载下的性能优化。后续 Redis 模块应聚焦 L2 共享、降级、TTL、穿透和多实例语义，并在更接近下游昂贵查询的场景下评估收益。
