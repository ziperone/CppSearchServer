# 网络与并发实现

## 请求处理链路

1. 主网络线程在监听 fd 就绪时循环 `accept`，把连接创建任务交给一个子网络线程。
2. 子网络线程将连接 fd 以 `EPOLLIN` 注册到自己的 epoll 实例；连接对象负责输入缓冲、输出缓冲和关闭状态。
3. 可读时循环 `recv` 到 `EAGAIN`，从输入缓冲提取完整 HTTP 请求。
4. 连接对象将一次业务请求投递到工作线程池，自己回到 epoll 等待其他连接事件。
5. 工作线程完成检索后，把“写响应任务”放回原网络线程的任务队列，并写 eventfd 唤醒它。
6. 原网络线程把结果放入输出缓冲；`send` 不完整时临时关注 `EPOLLOUT`，全部发送后恢复 `EPOLLIN`。

## 为什么工作线程不能直接 send

socket、输出缓冲、epoll 关注事件、连接计时器和关闭状态都由同一个网络线程维护。工作线程直接写会带来：输出数据交叉、同连接响应乱序、epoll 状态竞争、计时器竞争，以及 fd 被关闭复用后的错误写回。

因此约束是：工作线程只计算，网络线程只管理连接和 I/O。

## Keep-Alive 与关闭语义

- `recv == 0` 表示对端不再发送，不代表本端已经发送完响应。
- 输入不足以组成完整请求时继续等 `EPOLLIN`；输出未发送完时继续等 `EPOLLOUT`。
- `Connection: close` 是单个 HTTP 请求的属性：该请求的完整响应发送后才关闭。
- 空闲定时器只关闭“没有输入、没有输出、没有业务处理中”的连接，避免中断慢任务或部分响应。

## 并发与并行

epoll 的并发含义是只处理就绪 fd，避免一个慢连接阻塞整个 I/O 循环；它本身不让业务并行。真正的并行来自多个子网络线程和多个工作线程。一个连接内部仍保持串行，以保证 HTTP 响应顺序；多个连接的业务可同时计算。

## 关键取舍

- 使用水平触发（LT）：实现更稳健，未读完的数据会持续通知；ET 是后续可验证的优化方向，不能只改标志位。
- 使用 `eventfd` 唤醒网络线程：线程安全任务队列解决“任务在哪里”，eventfd 解决“阻塞的 epoll_wait 如何立即醒来”。
- 每个网络线程一个 epoll 实例：连接生命周期固定归属，减少跨线程共享连接状态。
