# 检索与缓存取舍

## 检索链路

1. 启动时读取 Markdown/TXT；Markdown 按标题层级切块，TXT 作为普通文本块。
2. 对每个块执行统一的分词和归一化，建立 `词 -> {块编号, 词频}` 的倒排索引。
3. 查询使用相同分词逻辑，多关键词按并集召回，优先覆盖更多查询词，再按词频分数取 TopK。
4. 返回标题路径、来源、正文片段和分数的 JSON。

这套设计避免每个请求遍历所有文档；它是关键词证据检索，可作为后续 Agent/RAG 的一个分支，但不替代向量召回。

## 两级缓存设计

```text
worker-local L1 -> Redis L2 -> 内存倒排索引
```

- L1：每个工作线程独占，避免全局 LRU 锁竞争。
- L2：Redis String 存储“一个 query 对应一整份 JSON”，用 `SET EX` 原子写入与 TTL 绑定。
- Redis 客户端也是 worker-local；同步 Redis 调用最多阻塞当前工作线程，绝不阻塞网络线程。
- Redis 故障时 fail-open，回源内存索引。

## 为什么默认关闭缓存

同一 Release 二进制、4 个工作线程、4 个 I/O 线程、`wrk -t4 -c256 -d30s --latency`、热点查询 `epoll`，每种模式运行三次：

| 模式 | 平均 QPS | 平均 P99 |
|---|---:|---:|
| 无缓存 | 375,418 | 0.94 ms |
| L1 | 296,273 | 1.29 ms |
| L1 + Redis | 283,297 | 1.32 ms |

当前内存索引检索太轻，缓存自身的 map/list/mutex、字符串处理和 Redis 网络开销大于省下的计算，因此默认 `none`。这不是“Redis 没价值”，而是“当前数据规模和工作负载不适合把缓存作为单机默认加速器”。

当接入 MySQL、真实密文检索、跨实例访问或更重的下游时，缓存价值必须重新用同一方法验证。

## L1 与 L2：共享结果，不同步缓存内容

L2 的目的不是把每个 Worker 的 L1 做成内容完全相同的副本，而是让不同 Worker 或不同服务实例在 **L1 未命中** 时复用同一份查询结果：

```text
Worker A：L1 命中 -> 直接返回本地 JSON，不访问 Redis
Worker B：L1 未命中 -> 查询 Redis L2 -> 写入自己的 L1 -> 返回同一份 JSON
```

每个 L1 的容量、淘汰顺序和已缓存查询可以不同，这是预期行为。当前文档索引在服务启动后只读、同一版本的查询结果是确定的，因此 L1 是否命中只影响延迟和下游负载，不会导致用户得到不同的检索内容。

真正需要一致性治理的是“索引或文档内容更新”。当前版本尚未支持在线更新；未来接入 MySQL 和增量索引时，应把共同的 `index_version` 放进缓存 key。版本变更后新查询使用新 key，旧 L1/Redis 条目自然不再命中；只有对内存和空间有更严格要求时，再增加发布订阅或显式失效通知。
