# 公开项目讲解提纲

## 90 秒版本

我做的是一个面向个人求职知识库的 C++ 本地文档检索服务。它在启动时把 Markdown 和 TXT 按标题切块，构建倒排索引；用户通过 HTTP 查询关键词，服务返回排序后的文档片段。

网络层不是停留在一个阻塞式 WebServer。我先实现非阻塞 epoll 驱动的连接处理，再把连接读写、Keep-Alive、半关闭和空闲超时放在网络线程里管理。业务检索交给工作线程池，结果通过 eventfd 回到原来的网络线程写出，这样工作线程不会直接碰 socket、输出缓冲或定时器，也避免了同一连接的响应乱序。

压测过程中我没有假设“多线程和缓存一定更快”。单 Reactor 受 I/O 收发限制后，我演进为主 Acceptor 加多个子 Reactor；缓存则做成可切换的 L1 和 Redis L2，并在同一 Release 负载下分别压测三次。结果是当前小型内存索引下无缓存约 37.5 万 QPS，反而高于 L1 和 Redis 模式，因此默认关闭缓存。后来再加请求阶段指标和 perf，确认轻量查询主要消耗在 JSON 构造、字符串分配和跨线程回传，而不是索引匹配。这个过程让我形成的习惯是：先明确连接所有权和正确性边界，再用数据决定优化方向。

## 值得引导追问的两个点

### 为什么工作线程不能直接写 socket？

网络线程独占连接状态：socket、输出缓冲、epoll 读写关注、计时器和关闭流程。工作线程直接写会造成数据交叉、响应乱序、fd 复用误写和状态竞争。解决方式是工作线程仅提交结果，由 eventfd 唤醒连接所属网络线程完成写回。

### 为什么缓存实现后默认关闭？

缓存的价值不是“技术栈里有 Redis”，而是省下的下游计算必须大于缓存维护成本。当前倒排索引计算很轻，L1 的数据结构和 Redis 调用反而增加了开销；但 Redis 的跨实例共享能力仍对未来 MySQL 或密文检索有价值，因此保留为可选路径并记录了反例数据。

## 表述边界

- 说“完成多实例 Redis 缓存共享验证”，不说“已经实现分布式系统”。
- 说“为真实密文检索预留服务承载能力”，不说“已经完成密文检索”，除非算法、正确性和性能实验已真实接入。
- 说“当前数据下缓存变慢”，这比宣称未经验证的加速更能体现工程判断。
