# 性能证据与复现

## 统一原则

性能结论只在固定构建、数据集、请求模型与线程配置下比较；报告 QPS 时必须同时看 P99、错误率、CPU/RSS 和必要的阶段耗时。平均值不能掩盖尾延迟。

## 关键演进证据

| 改动 | 观察到的结果 | 结论 |
|---|---|---|
| Keep-Alive | `wrk -t4 -c64` 下 QPS 约从 49,815 提升到 97,508，P99 从 1.58ms 降至 1.27ms | 连接复用减少建连与关闭的系统调用成本 |
| WorkerPool | 单连接会增加调度开销；多连接、业务更重时能释放 I/O 线程 | 是否加线程取决于业务计算与调度成本之比 |
| 多 Reactor | 单 I/O 线程成为瓶颈后，增加 I/O Loop 能继续提高吞吐 | 瓶颈会在业务线程和网络收发之间迁移 |
| L1 / Redis | 无缓存 375,418 QPS 高于 L1 296,273 和 L1+Redis 283,297 | 缓存不是免费优化，当前默认关闭 |

## 请求阶段诊断

诊断模式下的 10 秒热点测试（4 Worker、4 I/O、256 连接、无缓存）得到：

```text
wrk: 368,394.51 QPS，平均 686.98us，P99 0.99ms
服务端阶段平均：
工作线程排队 180us
工作线程计算   6us
结果回到 I/O 175us
响应写入内核   5us
服务端总计   368us
```

服务端统计从“完整 HTTP 请求已组装”开始，到“响应写入内核发送缓冲区”结束，因此不能与客户端 wrk 端到端延迟直接相等。

## perf 证据

30 秒 CPU cycle 采样（RelWithDebInfo、无缓存、4 Worker、4 I/O、256 连接）：

```text
374,351.54 QPS，平均 671.47us，P99 1.06ms
44K 样本，0 丢样本
```

用户态热点集中在 `cfree` 5.75%、`std::ostream::put` 4.63%、`_int_free` 3.75%、`_int_malloc` 3.53%、`escapeJson` 2.93%、`malloc` 2.67%，调用栈指向 JSON 响应构造、字符串分配释放与异步结果回传。结论：小索引下检索匹配不是主要 CPU 热点，下一步应优先验证响应构造和任务对象开销。

注意：`malloc/_int_malloc`、`cfree/_int_free` 是同一调用栈的不同层，不能相加；未知内核地址受 `kptr_restrict` 限制，不做猜测。

## 复现命令

```bash
cmake -S . -B build-ralease -DCMAKE_BUILD_TYPE=Release
cmake --build build-ralease -j
ctest --test-dir build-ralease --output-on-failure

bash scripts/run_cache_benchmark.sh
DURATION=10s bash scripts/run_latency_breakdown.sh
DURATION=30 bash scripts/profile_cpu.sh
```

`profile_cpu.sh` 需要 `kernel.perf_event_paranoid <= 1`。完整 perf 原始文件保存在私有面试资料目录，不上传 GitHub。
