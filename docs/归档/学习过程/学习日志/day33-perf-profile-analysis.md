# Day 33：用 perf 让性能结论落到函数级

## 这一步补上了什么

此前我们已经用 QPS、P99、CPU 和阶段耗时判断过：轻量检索下，线程排队和结果回传的时间大于实际检索时间。但这个判断还不够细，无法决定优化应该先动检索、锁、网络，还是响应构造。

今天通过 `perf record` 采样 CPU cycle，把问题从“感觉开销在这里”推进到“这些函数确实在消耗 CPU”。

## 结果怎么读

30 秒固定负载下，服务达到 `374,351.54 QPS`、P99 `1.06ms`，采到 44K 个样本且无丢失。用户态热点集中在：

1. `escapeJson` 和 `std::ostream::put`：把检索结果转成 JSON 的字符处理。
2. `malloc`、`_int_malloc`、`cfree`、`_int_free`：高频响应下的字符串扩容、临时对象与回调对象创建释放。
3. `pthread_mutex_lock/unlock`：任务队列交接的同步成本。

因此，这一阶段最合适的下一次优化尝试是减少响应构造时的分配和流式输出，而不是继续优化已经很快的倒排索引。

## 面试时怎样讲

“我没有只看 QPS 就认定瓶颈。我先在服务里把请求拆成排队、计算、结果回传、写响应几个阶段，发现检索只占约 6 微秒；再用 perf 对固定负载采样，热点集中在 JSON 转义、字符串分配释放和任务回传的锁。这样下一步优化就有证据：先减少响应构造和对象分配，再用同一负载复测，而不是盲目加线程或改索引。”

## 注意点

- self overhead 和 children 的累计调用栈不是同一个口径，不能相加。
- 当前结论只适用于小型内存索引和 `epoll` 热点查询；真实密文检索、更大文档集或 MySQL 下游可能把热点迁移到业务计算或 I/O。
- 内核地址因 `kptr_restrict` 不可解析，不对这部分样本做猜测。
