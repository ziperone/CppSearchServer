# Day 10：性能基线与瓶颈假设

## 本日目标

建立可复现的 Release 压测基线，在优化前用数据定位瓶颈候选，避免凭感觉引入线程池、缓存或 Redis。

## 压测方法

- 工具：`wrk` 4.1.0。
- 构建：Release。
- 请求：`GET /search?q=epoll`，另测多关键词和无命中路径。
- 并发梯度：c1、c16、c64、c256。
- 每轮：30 秒，使用 `--latency`。
- 资源监控：`pidstat -u -r -d`，与 wrk 测试时间对齐。

完整原始数据见 `docs/归档/原始实验/性能原始报告/baseline-loopback-2026-08-11.md`。

## 读数原则

- QPS 表示成功请求吞吐。
- P50 表示典型延迟，P99 表示长尾延迟，不能只看平均值或 QPS。
- c1 表示单连接串行请求的基础延迟；提高 c 会提高并发度并可能提高吞吐，但也会产生排队。
- 结果要重复运行，单次 QPS 存在正常波动。

## 结论

- c64 附近吞吐约 5 万 QPS，c256 无有效吞吐增长却显著抬高 P99，出现饱和拐点。
- c1 P99 为 88us，c64 P99 至少 1.58ms，确认并发排队是长尾延迟的重要来源。
- c64 资源监控：平均 CPU 93.28%，其中用户态 30.03%、内核态 63.25%；RSS 约 3.3MB，磁盘 I/O 为 0。
- 当前最强假设是单 EventLoop 串行路径与短连接 `accept/recv/send/close` 的内核态成本共同形成吞吐平台。它是待验证假设，而不是唯一已证实根因。

## 性能工程循环

```text
定义固定场景
-> Release 构建与正确性测试
-> 预热
-> 并发阶梯压测
-> 在饱和点监控 CPU/RSS/I/O
-> 提出可验证假设
-> 一次只改一个优化点
-> 用相同场景重测并比较
```
