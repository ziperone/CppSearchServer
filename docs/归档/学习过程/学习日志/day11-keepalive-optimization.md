# Day 11：Keep-Alive 连接复用优化

## 本日目标

验证前一轮压测中“短连接的内核态网络成本较高”这一假设，并让服务器支持一条 TCP 连接上的顺序多请求和已缓冲请求。

## 为什么现在做

短连接基线在 `c64` 下约为 4.98 万 QPS，`pidstat` 显示 `%system` 为 63.25%，高于 `%usr` 的 30.03%。这意味着优化前不应直接引入线程池，而要先用一个小且可验证的改动确认连接生命周期是否是主要成本来源。

## 实现

- HTTP 响应改为 `Connection: keep-alive`。
- `TcpConnection` 引入 `peer_closed_`：对端半关闭写端时，不立即丢弃尚未发送的响应；先发送所有已生成响应和输入缓冲区中完整的后续请求，再关闭连接。
- 发送完成后取消 `EPOLLOUT`，重置 `response_ready_`。若 `input_buffer_` 里已有下一条完整请求，直接调用 `processRequest()` 并继续发送；否则回到 `EventLoop::loop()` 等待下一次 `EPOLLIN`。
- `processRequest()` 只负责“取一条完整请求、生成一份响应、写入输出缓冲区”，不再递归调用 `handleWrite()`。发送循环统一由 `handleWrite()` 管理，避免多条流水请求导致递归调用链增长。

## 顺序与状态保证

1. `response_ready_` 为真时，不会处理下一条请求，先保证当前响应完整发送。
2. `send()` 返回 `EAGAIN` 时注册 `EPOLLOUT`；下一次可写再继续从 `output_buffer_` 发送。
3. 当前响应发送完成后，才从 `input_buffer_` 处理下一条完整请求，因此响应顺序与请求顺序一致。
4. 客户端在服务器处理期间发送的新数据会留在内核接收缓冲区；单线程 EventLoop 不会被中断，当前回调结束后会在后续 `epoll_wait` 中收到对应的 `EPOLLIN`。

## 验证

- Release 构建的既有 7 个测试全部通过。
- 手工 TCP 冒烟测试：同一 socket 上顺序发送两次 `/search` 请求，均得到正确的 HTTP 200 与对应检索结果。
- 手工流水测试：一次写入两条请求后执行写端半关闭，服务端返回两份完整响应，再关闭连接。
- 压测：`wrk -t4 -c64 -d30s --latency http://127.0.0.1:18088/search?q=epoll`。

## 结果与结论

Keep-Alive 达到 97,507.55 QPS，对比短连接的 49,815.34 QPS 提升 95.7%；P99 从 1.58ms 降至 1.27ms；`%system` 从 63.25% 降至 36.80%。

结论：短连接的建连与关闭成本确实是当前小数据集下的关键瓶颈之一。连接复用以很小的状态机改动带来了接近翻倍的吞吐提升，但当前服务依旧是单 EventLoop，尚未实现真正的多核并行处理。

## 复盘问题

为什么 `handleWrite()` 在当前输出缓冲区清空后，要先 `disableWriting()`，再判断输入缓冲区是否有下一条完整请求？

答案：输出已经清空后继续保留 `EPOLLOUT` 会使 socket 经常处于可写状态，导致无意义唤醒；先取消写关注，再根据已缓存请求生成新响应。只有新响应发生部分发送且遇到 `EAGAIN` 时，才重新注册 `EPOLLOUT`。
