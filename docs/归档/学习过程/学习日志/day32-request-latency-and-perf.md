# Day 32：请求分阶段耗时与 CPU 采样准备

## 今天解决什么问题

前面的压测能回答“QPS、P99 和 CPU 有没有变化”，但回答不了“一个请求的时间具体花在哪里”。因此补充可选的请求分阶段耗时统计，并为函数级 CPU 采样准备独立脚本。

## 请求在服务端经过的阶段

1. 收到一条完整 HTTP 请求后，准备进入工作线程队列。
2. 工作线程实际开始计算。
3. 工作线程完成检索，结果通过任务队列和 `eventfd` 回到原网络线程。
4. 网络线程首次向内核发送响应。
5. 响应字节全部写入内核发送缓冲区。

统计默认关闭，启动服务时最后一个参数传入 `on` 才启用；`GET /metrics` 可以读取累计平均值。工作线程仍然只记录时间和回传结果，绝不直接操作 socket、连接缓冲区或 epoll 状态。

## 关键实现取舍

- 每条请求携带自己的时间线对象，避免多连接之间串数据。
- 汇总值使用原子累加，只保留统计需要的总和与最大值，不为每个请求长期保存记录。
- 只有所有阶段均已打点、且响应已开始写出时，才计入指标。这样未来某条异常路径少打一个点，不会把未初始化的时间点算成错误的超大延迟。
- 指标会带来额外开销，因此它是诊断模式，不能和关闭指标时的 QPS 直接作绝对比较。

## 真实运行数据

环境：远程 Linux、Release、4 个工作线程、4 个网络线程、`wrk -t4 -c256 -d10s --latency`、无缓存、热点查询 `epoll`。

```text
wrk: 368,394.51 QPS
wrk 平均延迟: 686.98us
wrk P99: 0.99ms

服务端分阶段平均耗时：
工作线程队列等待: 180us
工作线程检索计算:   6us
结果回到网络线程: 175us
响应写入内核:       5us
服务端总耗时:     368us
```

这组数据说明：在当前小型内存索引下，检索计算本身很轻，更多时间花在线程池排队和跨线程把结果交回网络线程。它不是“跨线程设计一定错误”的结论；接入更重的 MySQL、RAG 或真实密文检索后，应重新测量。

服务端统计从“完整请求已组装”开始，到“响应写入内核发送缓冲区”结束；`wrk` 从客户端视角测量完整往返。因此 `368us` 不等于 `wrk` 的 `687us`，二者不能混用。

## perf 采样准备与限制

新增 `scripts/profile_cpu.sh`：独立构建带调试符号和 frame pointer 的 `RelWithDebInfo` 版本，再用 `perf record` 对固定负载采样，输出 `perf.data` 与文本报告。

远程机器当前 `perf_event_paranoid=4`，普通用户无权执行 `perf record`。脚本已经在采样无法启动时提前报错，避免压测跑完却误以为拿到了火焰图。没有管理员明确授权时，不尝试绕过此限制。

## 这次遇到的真实问题

第一次接入时间线时，曾在一次函数调用中同时把同一个智能指针作为实参传递、又在 lambda 捕获中 `std::move` 它。C++ 对实参求值顺序不保证，导致工作线程偶尔拿到空指针，统计出现不可信的大数值。

修正方式：先复制一份单独传给工作线程，再把原指针移动到回调捕获中。这个问题值得记住：同一表达式里不要依赖多个实参的求值先后关系。
