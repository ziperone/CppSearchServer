# Day 34：高性能服务最终追求什么

## 先纠正一个想法

一个好服务不追求“绝大部分耗时必须落在某个模块”，也不追求 CPU 永远 100%。它追求的是：在约定的正确性、延迟和可用性目标内，用可接受的机器成本稳定处理目标负载；超过容量时也能有边界地降级，而不是排队爆炸、内存耗尽或连锁超时。

因此，瓶颈不是必须消灭的敌人，而是容量边界。好的系统知道瓶颈在哪里、何时到达、到达后如何保护自己。

## 什么样的瓶颈是健康的

健康瓶颈通常有四个特征：

1. **预期内**：它来自业务计算、网络带宽、磁盘/数据库或真实下游依赖，而不是无意义的轮询、锁竞争、重复拷贝或内存抖动。
2. **可度量**：能够用阶段耗时、队列长度、CPU、I/O、错误率和 P99 说明它出现在哪里。
3. **有边界**：接近极限时有排队上限、超时、拒绝或降级，避免请求无限堆积。
4. **可扩展**：增加 CPU、实例、分片或连接池时，能按预期获得收益，直到下一个资源成为瓶颈。

例如真实密文检索耗时较长时，工作线程的 CPU 计算占主要比例是合理的；文档从 MySQL 读取时，下游 I/O 等待占比高也可以合理，前提是连接池、超时和熔断限制住排队。

## 什么样的瓶颈不健康

- 业务计算只有很小一部分，时间主要消耗在锁竞争、线程切换、对象分配、序列化或重复数据拷贝。
- 平均延迟看似正常，但 P99/P999 随连接数增加急剧恶化，说明队列开始放大尾延迟。
- CPU 还没被有效用于业务，线程池、单个网络线程或共享锁就已形成排队点。
- 过载时继续接收无限请求，导致内存、文件描述符或下游连接耗尽，最终全体请求超时。

## 生产系统真正盯住的指标

对交互式搜索服务，可以先定义这样的目标：

```text
正确性：结果正确、同一连接响应顺序正确、无资源泄漏
延迟：99% 请求端到端延迟 <= 某个业务可接受阈值
可用性：成功率 >= 某个目标，超时和 5xx 计入失败
容量：在目标 QPS、连接数和数据规模下仍满足前两项
成本：每请求 CPU、内存、网络和下游资源处于可接受范围
过载：超过容量后快速拒绝或降级，不把正常请求一起拖慢
```

阈值不是从机器跑分倒推，而是先从用户或调用方能接受什么倒推。例如交互检索更看 P99；离线批处理更看吞吐和整体完成时间。平均值只能辅助判断，不能替代分位数。

## 指标如何服务于决策

1. 先固定请求模型、数据规模和正确性校验，得到基线。
2. 增加负载，找到 QPS 不再增长、P99 开始明显恶化或错误率上升的拐点。
3. 用 CPU、RSS、上下文切换、队列长度、阶段耗时、perf 调用栈定位该拐点的资源。
4. 只针对证据最强的一个点做改动，并在相同负载下 A/B 对比：吞吐、P99、错误率和资源成本是否同时可接受。
5. 优化后瓶颈会迁移，重新测量，而不是假设旧结论永远成立。

## 放回当前项目

当前小型内存倒排索引下，阶段统计显示检索计算约 6us，工作线程排队与结果回传各约 180us；perf 又显示 JSON 转义、字符串分配释放和锁处于热点。因此当前的“不健康固定成本”主要是轻量请求下的框架与响应构造开销，而不是索引算法。

这不意味着立刻删除工作线程池。项目未来要承接真实密文检索或数据库访问，业务计算变重后，线程池的收益可能超过调度成本。正确做法是保留连接所有权和顺序保证的架构边界，在相同负载下尝试减少响应构造与任务对象开销；接入更重下游后重新测量。

## 面试中的一句话

“我不认为高性能服务要把瓶颈藏起来。目标是在既定 P99、成功率和成本下，让瓶颈落在可预期、可扩展的业务或资源上，并在过载时有边界。当前项目用阶段指标和 perf 证明，轻量查询的成本主要在响应构造和跨线程调度，所以我不会盲目加线程，而是按证据优化并复测。”
