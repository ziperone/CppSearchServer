# Day 25: 缓存不是免费的

## 预期与实际

预期：热点 `epoll` 查询命中 L1 后跳过检索，QPS 应提高。

实际：固定 I/O=4、Worker=4、c256 后，热点 L1 为约 28-30 万 QPS，低于未接 L1 时约 36-38 万 QPS；P99 也从约 0.98ms 上升到约 1.30ms。

## 为什么会这样

缓存确实降低了 Worker CPU：约 76% 降至约 44%，证明业务检索被跳过。

但每一次 hit 都在同一个 mutex 下修改精确 LRU 的 list 顺序。对于短小的内存检索，缓存锁竞争、哈希查找、TTL 检查、list 操作与字符串复制的成本超过了原本的检索成本，因此总 QPS 下降。

## 这次复盘的价值

不能说“缓存一定降低延迟”。正确说法是：

```text
缓存收益 = 被省掉的下游工作 - 缓存命中路径成本
```

只有前者明显大于后者，缓存才会提高吞吐或降低尾延迟。

Redis 同样不是魔法。它多了网络往返，单机轻量计算场景可能更慢；它的工程价值在多实例共享、保护慢下游、缓存昂贵数据库/RAG/远程调用结果。

这次反例应在面试中主动表达：我不仅验证缓存正确性，也压测了命中路径，发现全局精确 LRU 在微秒级查询中产生锁竞争，所以没有把它包装成虚假的性能收益，而是给出 per-worker cache、分片 cache、近似 LRU 与按成本启用缓存等后续方案。
