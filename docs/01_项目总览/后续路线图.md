# 后续路线图

## 当前完成状态

第一阶段“可运行、可解释、可压测的 C++ 搜索服务”已经完成：网络并发、连接治理、检索、缓存取舍、性能诊断和公开项目表达均具备。

## 下一阶段优先级

### 1. 先做有证据的轻量优化

perf 显示当前热点集中在 JSON 转义、字符串分配释放和跨线程任务交接，而非倒排索引匹配。下一次改动应只选择一个点，例如预留响应容量、减少 `ostream` 写入或减少任务对象复制，然后用同一负载 A/B 复测 QPS、P99、阶段耗时和热点变化。

### 2. 接入 MySQL 作为权威元数据源

MySQL 负责文档元数据、分类、版本和更新记录；内存索引负责在线检索；Redis 继续作为版本化查询结果缓存。先定义文档更新如何触发索引重建与缓存失效，再实现数据访问层。

### 3. 接入真实密文检索实验

只有把研究生课题中的密文检索算法接入真实查询路径，并记录正确性、延迟和资源数据后，才能将项目表述为“明密文检索服务”或关联具体科研课题。此阶段预计会让业务计算变重，届时重新验证 WorkerPool、缓存和批处理的收益边界。

### 4. 再讨论多实例部署

当单机容量边界、文档规模和更新一致性需求明确后，再设计负载均衡、索引分片、版本一致性和故障恢复。没有真实需求时不提前堆砌“分布式”模块。

## 每次改动的验收标准

1. 正确性和现有连接所有权边界不被破坏。
2. 固定构建、数据集、请求模型和连接数，做对照压测。
3. 同时报告 QPS、P50/P99、错误率、CPU/RSS、阶段耗时或 perf 热点。
4. 只有吞吐或延迟收益与额外复杂度匹配，才保留改动；否则记录结论并回退方案。
